现在聊起 AI 写代码，大家最常抱怨的就是随着项目推进，代码库里会迅速堆积起大量难以维护的“AI Slop”（低质冗余代码）：违反原本的业务逻辑、无视项目中已有的工具函数重复造轮子、满屏都是过度防御的判空与异常捕获、顺手写出一堆没人要求的额外实现，甚至时不时夹杂着一些让人啼笑皆非的低级错误。

很多人习惯把这些问题归咎于模型能力不够，或是提示词写得不够精细。但在我看来，真正的病根往往出在动手写代码之前：**绝大多数开发者在打开对话框的那一刻，其实根本没有想清楚自己到底要做什么，脑海里对代码最终应该长成什么样，缺乏一个具象的想象。**

当你带着一个模糊的念头去让模型干活时，模型会非常积极地接管所有主动权。它会替你发散出长篇累牍的分析，设想十几种边缘场景，抛出一连串设计选型问题，或者直接甩给你一套庞大繁复的架构方案。面对这种瞬间涌来的信息轰炸，人脑很容易陷入一种**“认知负债”**——模型生成的思考量和方案复杂度，远远超出了你当下能够消化的阈值。一旦认知过载，人最本能的反应就是**“认知投降”**：算了，既然它想得这么周全，就全交给它看着办吧。从缴械投降的这一刻起，代码就已经彻底脱离了使用者的约束。

平心而论，重复造轮子、过度防御、违背业务直觉这些问题，在过去的“古法编程”时代同样司空见惯，人类程序员写代码也不可能不犯错。但区别在于，古法编程的时代追求的是慢和稳。人类手敲代码的速度天然限制了系统膨胀的速率，团队有充足的时间去开会讨论方案，去逐行做 Code Review。而在当下，AI 输出代码的速度太快了。如果我们还试图沿用过去的节奏，靠人眼去逐行审视它产出的每一处细节，那么开发者自己就会变成阻塞开发进度的最大瓶颈。

所以，在 AI Coding 时代探讨“如何提高代码质量”，本质上是在解一道吞吐量与控制力的矛盾题：**当人类不能成为开发流程的阻塞环，又绝不能向模型陷入认知投降时，我们究竟该靠什么把代码质量框住？**

## 重构优先于预先设计：真正的架构始于第一版原型撞墙之后

为了防止模型乱写，社区里很推崇“先写详尽 Spec（规范文档）、把架构彻底定死再开发”的做法。过去我也很喜欢这套流程：先和 Agent 反复聊架构，等落出一份完整的 Spec 后再动手。

但实践多了就会发现其中的荒诞之处：**Agent 写出来的 Spec，你第一眼看上去永远觉得毫无破绽。** 它排版工整、术语高级、考虑周全，甚至有些地方复杂到让你读着都觉得有认知压力。可一旦顺着这份看似完美的 Spec 把代码写出来，到头来往往还是要推翻重改。

原因很简单：如果你此前没有做过高度相似的系统，你根本不知道这个领域里真正的“决策点”藏在哪里。面对一个架构问题，模型可以自己造一套方案，社区里也有成熟的开源方案，但如果你没有踩过对应的坑，你连它们各自的权衡点（Trade-off）是什么都无从感知，又怎么可能在写代码前仅凭一份文档做出正确的取舍？反过来说，如果一个开发者真有本事在没写一行代码前就把所有边界和接口约束想得滴水不漏，那他本来就不太可能写出失控的 AI Slop。

既然在空白状态下硬憋架构本质上只是一种幻觉，不如承认现实：**让重构优先于预先的完整架构设计——用实验去代替空想，先实践，再思考。**

拿我最近在做的开源项目 **Seamline** 来说，它是一个用来解决 AI Agent 流式传输中断后“断点续传”的中间件。立项之初我只看了个大致的架构方向，并没有死抠每一个细节，而是先让模型快速搭出了第一版原型。

在断点续传的游标设计上，模型最初自己选择的是**“消息型游标”**——也就是在服务端把流式吐出的一个个 Token 切片堆叠拼接成完整消息，以消息为单位来维护游标。看 Spec 的时候，你会觉得这套逻辑挺顺畅的；直到原型写完、跑起端到端测试时，雷才真正炸开：大模型吐出来的不只是普通文本，还经常包含工具调用的参数等格式化 JSON。当服务端只靠消息型游标把零散的 Token 切片粗暴堆叠在一起时，根本无法判断半截 JSON 的特定结构，解析直接就崩了。

遇到这个问题后，我起初完全交给了 Agent 去修。Agent 的解法非常“大模型”：**它在原有的消息拼接逻辑外面打了一层专门的补丁，去单独解析这种 JSON 格式化输出。**

但这立刻引出了新的问题：今天你为了 JSON 打一层解析补丁，那明天模型吐出复杂的 Markdown 结构需要流式渲染呢？或者多路工具调用交错输出呢？你会发现，顺着这个路子走下去，修好一个 Bug 的同时必然在给下一个坑埋雷，模型的解决方案永远是不断往上叠补丁。

就在模型准备继续砌第二层补丁的时候，我意识到底层路子走歪了：消息型游标根本不适合大模型这种原生流式系统。于是我叫停了修补，让模型去横向调研社区里的成熟开源方案，看看像 Codex、Centrifugo 这些系统是怎么处理的。对比之后豁然开朗——社区成熟方案采用的几乎都是**“事件型游标”**。它根本不关心你在传什么内容，也不在服务端做任何切片拼接，而是直接以单调递增的事件 ID 作为游标，载荷完全透明。这种设计天然就契合 Agent 的消息通信。

那这是否意味着“消息型游标”本身就是错的？其实也不是。两种游标都能做断点续传，只是**工程取舍的权衡点不同**：如果选消息型游标，存储看似直观，但你必须在续传和解析策略上打无数额外补丁来擦屁股；而如果选事件型游标，传输和续传极其干净，但每一个 Token 切片都成了独立事件，你就必须在存储层（比如热窗口环形缓冲和内存配额）上花心思做空间优化。

你看，如果没有先让模型把那个有瑕疵的原型跑起来、没有亲眼看到它为了 JSON 解析去打补丁，在项目第一天对着空白文档聊架构时，缺乏同类经验的我是绝对想不到“消息游标 vs 事件游标”这一层权衡的。当你看到原型撞墙、看到冲突点摊在眼前时，脑海里的架构脉络才会真正清晰起来。这时候再果断介入，对原型做“减脂”、拆解和架构重构，才是真正有效的架构设计。

## 对抗注意力稀释：从降复杂度自审到团队的多层防线

就像上面在 Seamline 里看到的，如果完全把项目交给模型而缺乏人工判断，模型一定会顺着阻力最小的方向不断堆叠补丁，把系统复杂度推向失控。

为了在日常开发中管住模型，我们通常会在仓库里放一份 `AGENTS.md` 或 `CLAUDE.md`，写明代码规范与架构红线。这很有必要，但不能对它抱有不切实际的指望。在长程开发里，模型有明显的**注意力偏移**——随着上下文窗口被海量的代码和对话填满，规则文件占的比重越小，模型就越容易无视它。所以写在文档里的规则，开发者自己心里也得时刻装着，在关键节点上主动去拽住模型的缰绳。

到了 Code Review 环节，既然人的阅读速度跟不上 AI 的产出速度，审查就必须高度聚焦。我给个人 Review 定的核心标尺，来自《软件设计哲学》（*A Philosophy of Software Design*）的核心观点：**控制并降低系统复杂度。**

模型写代码最常见的毛病就是“过度防御”和“额外实现”——到处套无意义的判空和异常兜底，或者顺手写一堆没要求的功能。为了高效拧干这些水分，我现在的做法是**“带指令的 Agent Review + 人工只看核心代码”**。

在人工介入前，先让 Agent 做一轮审查，但不是泛泛地找 Bug，而是强制它额外检查三件事：
1. **有没有可以简化的代码？**
2. **有没有过度防御、做额外实现的逻辑？**
3. **审查找出来的 Bug，在真实业务场景下真的容易发生吗？**

第三问非常关键。如果不加这层过滤，Review 模型往往会为了凑数找出一堆极端假想条件下的伪 Bug，反过来逼着编码模型打上更多防御性补丁。等 Agent 把外围的冗余和过度防御筛掉一轮后，我只去审最核心的业务代码。有时候遇到自己完全不熟悉的编程语言，也没必要去死磕语法细节，直接让模型把实现逻辑讲清楚，人只把精力放在**审视实现逻辑的合理性与系统复杂度**上。

而在团队协作的层面上，更不能因为“本地跑通了”就绕开 Review 流程。模型为了快速交差，有时会写出极其隐蔽的灾难级代码——比如我就见过模型写出**“先把数据库全表拉出来，接着在内存循环里做 `N + 1` 查询（单次请求直接打出几百条 SQL），最后再在 Python 内存里过滤状态”**的逻辑。最要命的是，在本地测试库只有几条数据的时候，这段代码的功能完全正常，返回值也毫无问题。如果团队没有严格的 Review 流程把关，这种写法大概率会一路绿灯合进主干，直到线上流量进来、直接把数据库和服务打崩的那一刻才会被发现。

在这方面，Anthropic 的 Claude Code 团队前阵子分享过一篇[他们如何解决高吞吐量代码审查的实践](https://claude.dev/blog/solving-code-review-at-anthropic/)。当他们内部 90% 的代码都由 Claude 生成时，传统逐行人工审核同样走不通了。他们的解法是把 Review 变成一套**七层漏斗体系**：
1. **提 PR 前的本地自验证**：给模型可执行的测试、构建或截图工具，在别人看到代码前先完成自我校验；
2. **PR 级多 Agent 并行审查**：多个 Agent 同时从不同角度找 Bug，再由另一组 Agent 对发现的问题投票过滤掉假阳性和纯风格噪音，只留下真正致命的问题；
3. **阻塞式自动化安全审查**：独立的安全 Agent 扫描，问题不解决或不给出合理解释就无法合并；
4. **刚性 CI 门禁**：Lint、类型检查与全平台构建测试；
5. **按风险分级的人工审批**：由分类器根据代码改动路径自动定级，低风险改动靠自动化直接放行，把人类工程师稀缺的注意力集中在架构变更与高风险核心路径上，同时严格执行“谁发起提示词，谁就为代码负全责”；
6. **合并队列与 Feature Flag 渐进灰度**：先对内部员工开启 Flag 试用，再逐步推向外部；
7. **快速观测与秒级回滚**：一旦漏网之鱼引发线上故障，不发版直接关停 Flag 回滚，并把每一次导致事故的 PR 沉淀为每日考核 Review Agent 的评测集（Eval）。

不管团队规模大小，这套思路的核心都是一致的：不靠人眼去当底层的语法和低级错误过滤器，而是用多道自动化防线先把那类“全表拉出加 `N + 1` 查询”的荒唐代码拦在门外，再把人的精力留给真正决定系统走向的架构与核心逻辑。

## 测试去伪存真：抛弃“为了变绿”的自嗨单测

敢于对原型大刀阔斧地重构，也敢于在 Review 时把视线集中在核心逻辑上，前提是手头有一套真正靠得住的测试。

在开发过程中，模型其实很爱自己写测试，但仔细看就会发现，**模型主动写出的大部分单元测试都是无效测试**。它们往往是顺着刚写完的代码逻辑反推出来的，纯粹是为了覆盖回归、为了“让测试变绿”而凑出来的用例。用同义反复的测试去测可能有问题的代码，根本覆盖不了真实的业务效果。

因此，我不再追求普通单元测试的数量，而是规定了三种必做的硬测试：

- **端到端测试（E2E Tests）**：就像 Seamline 里抓出 JSON 拼接问题的那次测试一样，绕开内部自欺欺人的局部 Mock，直接跑通从输入到输出的真实完整链路。
- **基于属性的测试（Property-based Testing）**：不靠模型编造那几个顺眼的固定输入，而是由人定义系统必须满足的不变式（Invariants），再用随机生成的海量边界输入去验证。
- **差分测试（Differential Testing）**：在对原型做“减脂重构”或切换底层实现时尤其管用。把同样的输入同时喂给重构前后的两套实现（或参考基准），严格比对输出是否一致，确保架构减脂没有破坏原有的正确行为。

## 证据驱动与“只复审一次”的熔断法则

最后一道防线，是交付验收与修 Bug 的止损纪律。

我要求模型的每一次交付都必须是**证据驱动**的，绝不轻信它口头的那句“已修复”。修完后端 Bug，必须拿出此前失败的 Bad Case 已经通过、**且其余所有存量测试零失败**的运行结果（修好旧 Bug 绝不能引入新坑）；改完前端界面，则必须交出真实渲染的验证截图。

而在修 Bug 的流程上，我坚持**“通常只复审一次”**。

就像前面 Seamline 游标那个例子，当模型提交了一次修复，复审发现它只是打了个拙劣的补丁、甚至引出了新问题，需要反复打回、反复复审时，就不要再在原来的代码上和它死磕了。有趣的是，Anthropic 在上面那篇审查文章里也踩过一模一样的坑——他们曾有一个 PR 在写代码 Agent 和审代码 Agent 之间一夜间自动来回改了五十多轮，最后排查发现，反复拉扯根本抓不出新问题，只会制造无意义的改动噪音，所以他们后来也强制加上了复审轮次上限，超限就要求作者停下来重想方案。

**一个问题如果需要反复复审都按不住，说明底层的抽象本身就错了。** 及时停手熔断，回退代码去调整架构，才是避免代码库滑向 AI Slop 的唯一正解。

说到底，模型只是帮我们省掉了敲键盘的时间，却没有替我们免除工程上的判断。承认自己在项目起点想不清全貌，先拿粗糙的原型探清痛点，再靠减脂重构、分层 Review、硬核测试和及时熔断把代码一点点收紧——在没人有空慢下来逐行读代码的今天，这大概是我们既不阻塞进度、又能守住代码底线的最务实的办法。

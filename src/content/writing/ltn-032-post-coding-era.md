真正完全靠自己一行行手敲代码的日子，仔细想来，其实只停留在我的大一。

从那之后，AI 几乎伴随了我整个技术学习的轨迹。从最早接触 Java，到后来写 Go，再到如今从事 Agent 相关的工作，我算得上是伴随大模型一起进入行业的这一代人。外人听见 Agent，有时会联想到某种制造通用智能、彻底取代人类的宏大叙事，但身处其中其实很清楚，有能力做那种底座级替代品的，全世界也只有极少数几家头部企业。对绝大多数身在一线的工程师而言，它和当年的云原生、测试开发或是运维开发没什么两样，只是一个细分的工程领域——大多数时候，我们只是在给一个已有的系统多装上一个智能化的业务模块。

真正让我感到恍惚的，不是手头开发的业务，而是自己与代码之间越来越远的距离。

最开始用 AI 时，我还会仔细审视它写出的每一行逻辑；再往后，只看个大概框架；到了今天，我几乎已经不再手写代码，甚至连看都不怎么看了。过去被视作质量底线的 Code Review，在我的日常里也渐渐退场。随着模型底座能力的提升，低级的编码错误越来越罕见，即便偶有疏漏，交给专门的 Review Agent 跑上一遍，也远比人眼排查更高效。

当一个程序员在日常工作里既不写代码、也不看代码时，我很难不陷入一种迷茫：在这个被称作“后编码时代”的当下，这份工作究竟还需要我做什么？

在很长一段时间里，我以为自己的角色是“调度者”。毕竟项目需求落在我头上，而我负责驱使 Agent 去完成开发。但这种自我定位越想越站不住脚。真正在和项目代码直接打交道的其实是 Agent，我聊需求是和它聊，盘架构也是和它聊。当它在工程实现上表现得越来越老练时，我对它的认知依赖也随之加深，直到某一天，我突然意识到主客关系已经悄然倒置了。

现在并不是我在使用模型，而是模型在使用我。

Agent 就像一个静静伫立在系统中央的中枢，它唯一欠缺的，只是一个启动信号，以及散落在代码库之外的业务背景。它潜在地支配着我去搜集零散的业务规则、拼凑上下文，再浓缩成一段提示词喂给它。在 Agent 的架构设计里，模型会挂载各种外部工具（Tool）来获取信息；而在真实的开发流程里，我自己恰恰成了被模型调用的那个外部工具。

之所以会如此顺理成章地交出主动权，归根结底也源于我思维深处的惰性。

我一直是个偏爱“确定性”、习惯直奔结果的人。平时打游戏，我最抗拒的就是复杂的分支探索——站在迷雾重重的岔路口不断试错，非但不会让我觉得有趣，反而只让我感到疲惫。我最舒服的状态，是直接看到一个清晰的目标和方向，不需要费神摸索，只要顺着一条明确的路一直走下去，直到拿到最终的结果。

放在过去，写代码偏偏是一场避不开的“分支探索”。尤其当接手一个超出自身能力范围的任务时，你必须在无数的报错和知识盲区里反复碰壁。那种漫长的试错在以前被称作“锻炼”，虽然痛苦，却是技术内功增长的唯一途径。

大模型的出现，恰好帮我略过了所有痛苦的探索过程，直接把确定的结果端到了面前。在它的加持下，我们可以轻易接下远超自身真实水平的工作，并在顺利交付的瞬间，生出一种“这个问题本就在我能力范围之内”的错觉。这层由模型赋予的“虚假数值”出现得越频繁，人自身的能力成长就越迟缓；而自身成长越慢，面对更复杂的难题时就越只能仰仗模型。当模型还在以远超人类的速度迭代时，这个死循环便彻底闭环了。

在这个闭环里，个人的基础编码能力正在迅速贬值。就像工业革命前的老工厂，力气大的人曾是车间里最优秀的工人；可一旦自动化机器进场，人的力气大不大，还重要吗？

当然，至少在眼下这个过渡期，人与人之间的差距并没有被完全抹平。

前阵子遇到一个棘手的工程问题，我用着市面上最顶尖的模型，反复尝试都卡在死胡同里；后来请教我的 Mentor，他只用了一个能力明显弱一截的模型，换了个切入角度，就引导模型给出了一个全新的解法。

那次对比让我看得很明白：大模型其实是一颗早就被海量训练数据填满的大脑，所有的知识与解法都已经潜藏在参数深处，而屏幕前的使用者，则是负责点火的神经元。能不能把沉睡在模型内部的正确数据唤醒，能不能激发出它的涌现能力，完全取决于使用者这颗神经元够不够活跃、够不够强大。在现阶段，工具依然由人主导，人的专业水位直接决定了 Agent 发挥的上限。

可看清这一点，并没有让我对行业的未来多出几分乐观。

因为坦白讲，日常绝大多数的开发工作，根本不需要去激发什么高深的涌现能力，也没有多少技术深度可言。只要团队里有少数几个能力极强的工程师把工作流搭建妥当，把协作机制理顺，剩下的日常研发，似乎只要是个足够聪明、具备基本开发概念的人就能胜任。甚至再往前推演一步，当基础编码与代码审查都不再构成门槛，以后这些工作，或许只需要逻辑严密、对业务理解透彻的项目经理就能直接挑起大梁。

至于程序员，则会从过去从事基础创造的劳动者，退化为系统背后的“修理工”。流水线正常运转时不再需要你亲自动手，只有当自动化机器偶发故障、出现 Agent 无法自愈的疑难杂症时，才需要你进场做一次检修。

许多人喜欢顺着这个逻辑给出一个光明的建议：既然如此，那就去修炼内功，去成为那个搭建工作流的人，去成为强大的“神经元”和不可替代的高级“修理工”。

可每当听到这种建议，我总觉得有一道迈不过去的坎：我的 Mentor 之所以能长成那样强大的神经元，是因为他在没有 AI 的年代里，实打实地手写过无数行代码，在无数次痛苦的分支探索里踩遍了底层的坑；而我们这一代从大二起就不怎么独立写代码、如今连代码都不再翻开的开发者，从一开始就活在模型提供的“虚假数值”里。当那条靠手写代码积累直觉的阶梯已经被抽走，一个从未亲手造过机器的人，究竟要靠什么才能凭空长出顶级的检修能力？

更何况，时间根本不站在我们这一边。程序员这个职业因互联网而生，互联网用了几十年的漫长生长，才铺就了这一整个行业与几代人的成长路径；而大模型的爆发，从真正进入大众视野到替代掉绝大部分日常工作，前后不过短短一年。几十年积淀下来的职业护城河，在以年甚至以月为单位的加速狂飙面前被轻易抹平。在这样的速率面前，过去那条“只要闷头写代码就能升级”的确定性主线早已消失，而我们现有的认知，甚至已经丧失了预测未来的能力。

既然讨厌在看不清终点的迷雾里做无休止的分支探索，面对这股无法预判的浪潮，我反倒倾向于接受一个虽然消极、但足够确定的结局：也许根本就不存在什么让大多数人都留存下来的转型方向，未来就是不再需要这么多人，而我们终究会被替代。
